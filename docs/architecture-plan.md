# План архитектуры: учёт складского LED-оборудования

Документ фиксирует research вариантов доставки, выбранный default для старта, высокоуровневую архитектуру и roadmap. **Код продукта на этом этапе не пишется** — только планирование под будущие интеграции (mapper, scan in/out, алерты занятости/нехватки, учёт часов и выездов).

---

## Решения MVP

Зафиксировано с заказчиком (2026-10-07). Эти решения — источник истины для scope фазы 1; предыдущие «открытые развилки» закрыты.

| # | Тема | Решение |
|---|------|---------|
| 1 | Единицы учёта | **По количеству (qty)** на старте: номенклатура + остатки. Серийный учёт экземпляров — позже. |
| 2 | Резервы / overbook | **Soft warning.** Заказ можно сохранить при дефиците; система поднимает сигнал нехватки и предлагает **арендовать снаружи** (внешний прокат). |
| 3 | Сканеры | **Вендор неизвестен** (скорее рамка с AliExpress). Без привязки к фирме: канонические **Scan Events** + адаптер; позже generic gate/frame webhook. |
| 4 | Исходные данные | **Greenfield** — склад сейчас не ведётся; миграции из Excel нет. |
| 5 | Контур MVP | **Складской учёт и заказы проката вместе** (не «сначала только склад»). |

Краткий scope MVP (фаза 1):

- Справочник номенклатуры (SKU / типы) и остатки **по количеству** (включая кабели/расходники)
- Локации склада (зоны/ячейки) без mapper
- Заказы проката: даты, состав по qty, soft-резервы
- При дефиците/overbook → alert `shortage` + действие/статус **«арендовать снаружи»** (`ExternalHire`)
- Ручной ввод движений + подготовка к scan-событиям (абстракция, без конкретного железа)
- Роли: склад + менеджер; greenfield, без импорта legacy
- Доставка: PWA (Next.js + TypeScript)

Вне MVP: серийники, mapper, hours/trips, конкретный драйвер рамки, native-клиент.

## 1. Контекст и роли

Компания сдаёт в прокат LED-экраны и сопутствующее оборудование (кабинеты, контроллеры, кабели, кейсы, крепёж). Нужна система учёта на складе с перспективой подключения уже работающих сервисов.

| Роль | Типичные устройства | Задачи |
|------|---------------------|--------|
| Склад | планшет / смартфон Android; позже — рамка/гейт на въезде | приём/выдача, инвентаризация qty, статусы остатков |
| Логистика | телефон в дороге, планшет в машине | выезды, комплектация рейсов (после MVP) |
| Менеджеры | ноутбук / десктоп | заказы проката, занятость, дефицит → внешняя аренда |

Ограничения склада: нестабильный Wi‑Fi в зонах, будущие scan-устройства вендор-независимы, уведомления о нехватке и необходимости внешнего проката, минимум трения при внедрении с нуля.

## 2. Research: варианты доставки

### Критерии сравнения

- Сканеры (камера, HID, будущая рамка/гейт — через абстракцию)
- Офлайн / плохой Wi‑Fi
- Push-уведомления
- Интеграции с внешними сервисами (HTTP/webhooks)
- Покрытие ролей (склад + логистика + менеджеры)
- Скорость MVP
- Стоимость поддержки одной команды

### Сводная таблица

| Критерий | PWA / веб | React Native | Flutter | Десктоп (Electron/Tauri) | Гибрид (веб + native) |
|----------|-----------|--------------|---------|---------------------------|------------------------|
| Скорость MVP | ★★★★★ | ★★★ | ★★★ | ★★ | ★★ |
| Один клиент для всех ролей | ★★★★★ | ★★★ (нет десктопа «из коробки») | ★★★ | ★ (плохо на складе) | ★★★★★ (дорого) |
| HID / ручной ввод кодов | ★★★★★ | ★★★★★ | ★★★★★ | ★★★★★ | ★★★★★ |
| Камера → QR/штрих | ★★★★ (BarcodeDetector / библиотеки) | ★★★★★ | ★★★★★ | ★★ | ★★★★★ |
| Офлайн | ★★★ (SW + очередь) | ★★★★★ | ★★★★★ | ★★★★ | ★★★★★ |
| Push | ★★★★ (Web Push) | ★★★★★ | ★★★★★ | ★★★ | ★★★★★ |
| Интеграции API | ★★★★★ | ★★★★★ | ★★★★★ | ★★★★ | ★★★★★ |
| Стоимость поддержки | низкая | средняя+ | средняя+ | средняя | высокая |
| Магазины приложений | не нужны | нужны | нужны | опционально | частично |

### Разбор по вариантам

**PWA / веб-приложение.** Один URL, установка на домашний экран планшета, менеджеры работают в браузере. Ручной ввод и HID-пистолеты (если появятся) работают как клавиатура. Камера закрывает QR. Рамка/гейт подключается **снаружи** через webhook scan events — клиенту не нужен native SDK вендора. Офлайн: Service Worker + IndexedDB + outbox. Web Push для алертов нехватки / внешней аренды. Быстрее всего довести MVP (склад + заказы) и стыковать HTTP-интеграции.

**React Native / Flutter.** Сильнее в фоне и железе, но дольше MVP и дороже поддержка; менеджерский десктоп всё равно потребует веб. Не оправдано, пока вендор рамки неизвестен и учёт qty-first.

**Десктоп.** Удобен офису, неудобен складу. Как единственный клиент — отпадает.

**Гибрид.** Имеет смысл как **фаза 3+**, если PWA упрётся в лимиты; бэкенд и контракт Scan Events сохраняются.

### Вердикт

**Старт: Progressive Web App на базе Next.js + TypeScript (единый веб-клиент + API).**

Почему:

1. MVP сразу закрывает склад и менеджерские заказы на одной поверхности.
2. Неизвестное железо рамки не блокирует старт: события скана — HTTP-абстракция.
3. Qty-учёт и soft-резервы — доменная логика на сервере; клиент тонкий.
4. Минимальная стоимость поддержки; native — эскалация по метрикам.

## 3. Рекомендуемый стек (MVP и рядом)

| Слой | Выбор | Зачем |
|------|--------|--------|
| UI + SSR/API | **Next.js (App Router) + TypeScript** | один репозиторий: UI склада/менеджеров + Route Handlers / BFF |
| Стили / UI-kit | Tailwind + shadcn/ui | формы учёта, заказы, таблицы, диалоги soft-warning |
| PWA | `@ducanh2912/next-pwa` или Workbox | офлайн-кэш каталога, installability |
| Клиентское состояние движений | IndexedDB (idb) + outbox | очередь stock/scan-событий при потере сети |
| БД (когда появится код) | PostgreSQL | остатки, заказы, алерты, внешняя аренда |
| ORM | Drizzle или Prisma | типобезопасные миграции |
| Auth (позже в реализации) | сессии / OIDC | роли склад / логистика / менеджер |
| Очереди / webhooks | worker или managed queue | приём scan/mapper без блокировки UI |
| Хостинг | Node-совместимый (Vercel / VM / k8s) | без привязки на этапе плана |

**Не брать на старте:** отдельный мобильный репозиторий, SDK конкретного вендора рамки, GraphQL «на всякий случай», микросервисы по одной интеграции, серийный контур как обязательный путь данных.

## 4. Архитектура модулей

```
┌─────────────────────────────────────────────────────────────┐
│                     PWA / Web Client                        │
│  Склад │ Менеджеры (заказы) │ позже Логистика               │
└───────────────────────────┬─────────────────────────────────┘
                            │ HTTPS
┌───────────────────────────▼─────────────────────────────────┐
│                 Core API (Next.js / BFF)                    │
│  Catalog │ Stock │ Rentals │ ScanEvents │ Alerts │ ExtHire  │
└───┬────────────┬────────────┬────────────┬────────────┬─────┘
    │            │            │            │            │
    ▼            ▼            ▼            ▼            ▼
 PostgreSQL   Outbox/Q    Webhooks in   Webhooks out  Files
                          (scan gate/    (alerts,
                           frame later)   notify)
```

### Модули ядра

| Модуль | Ответственность |
|--------|-----------------|
| **Catalog** | номенклатура LED и расходников (SKU), атрибуты, комплекты |
| **Stock** | остатки **по количеству** на локациях; движения приход/расход/перемещение |
| **Locations** | склад, зоны, ячейки; позже — mapper |
| **Rentals / Orders** | заказы проката, даты, строки qty, soft-резервы |
| **ExternalHire** | потребность «арендовать снаружи» при дефиците: qty, SKU, заказ, статус |
| **Scan Events** | канонические in/out/move (UI сегодня; gate/frame webhook завтра) |
| **Alerts** | soft-overbook, shortage, external_hire_needed; UI + push |
| **Integrations** | адаптеры scan gateway (generic), mapper, hours/trips, notifications |
| **Identity & RBAC** | пользователи, роли, аудит |
| **Serialized Assets** *(после MVP)* | экземпляры с серийниками поверх тех же SKU |

### Границы API для будущих интеграций

Контракты — **событийные + REST**, `/api/v1/...`. Ядро — истина по остаткам и заказам.

#### A. Mapper (после MVP)

- `GET /api/v1/locations` — зоны и якоря
- `POST /api/v1/integrations/mapper/sync` — привязка stock/location ↔ карта
- Исходящее: `location.updated`

#### B. Scan in / out (абстракция; железо неизвестно)

Каноническая модель **не знает вендора**:

```
ScanEvent {
  event_id,          // идемпотентность
  source: ui | hid | gate | frame | adapter:<name>,
  code | sku_hint,   // рамка может отдать код тары/паллеты/SKU
  direction: in | out | move,
  qty?,              // для qty-учёта; default 1
  device_id?,
  at, meta
}
```

- `POST /api/v1/integrations/scan/events` — батч событий (generic webhook для будущей рамки AliExpress / любого гейта)
- Адаптер нормализует проприетарный payload рамки → `ScanEvent` (отдельный модуль, без протечки вендора в ядро)
- Ответ: применение к Stock + возможные alert / ExternalHire ids
- Исходящее: `scan.accepted` / `scan.rejected`

На MVP: события создаёт UI (ручной ввод / камера). Контракт webhook уже существует «на бумаге», чтобы рамку подключить без перелома модели.

#### C. Occupancy / shortage / external hire

- Правила: пересечение резервов по SKU vs available qty → soft warning, не блок
- Alert types: `shortage`, `overbook_soft`, `external_hire_needed`
- `GET /api/v1/alerts?status=open`
- `POST /api/v1/external-hires` — зафиксировать внешний прокат (qty, supplier_note, linked order/alert)
- `POST /api/v1/integrations/notifications/dispatch` — наружу в notification-сервис

#### D. Hours / trips (после MVP)

- `POST /api/v1/integrations/trips`, `.../hours`
- Не входят в MVP-контур

Все интеграционные входы: HMAC, retry-safe, DLQ.

## 5. Модель данных (высокий уровень)

Qty-first (MVP). Серийный слой — аддитивное расширение, не замена.

```
Sku / ItemType     — номенклатура (LED cabinet P2.5, cable loom, flight case…)
                     track_mode: quantity | serialized  (MVP: только quantity)
StockBalance       — (sku_id, location_id) → qty_on_hand, qty_reserved
StockMovement      — append-only: in/out/adjust/move, qty, reason, order_id?
Location           — склад / зона / ячейка; optional mapper_ref
Kit / Bundle       — типовой комплект (состав SKU×qty)
RentalOrder        — заказ клиента, даты, статус
RentalLine         — sku_id, qty_requested, qty_soft_reserved
Reservation        — soft-резерв qty на интервал (не блокирует сохранение заказа)
ShortageSignal     — расчётный/сохранённый дефицит по SKU×интервал
ExternalHire       — «арендовать снаружи»: sku, qty, order_id, status
                     (needed → ordered → received → closed), supplier_note
ScanEvent          — append-only, vendor-agnostic (см. выше)
Alert              — shortage | overbook_soft | external_hire_needed | …
IntegrationCursor  — watermark синхронизаций
AuditLog           — кто двинул остаток / заказ
User / Role        — warehouse | logistics | manager | admin

# После MVP
Asset (serialized) — экземпляр serial/barcode, sku_id, status, location_id
```

Инварианты MVP:

- остатки меняются только через `StockMovement` (не «голый PATCH» баланса);
- `ScanEvent` иммутабелен; коррекции — компенсирующими событиями;
- **soft reserve:** заказ сохраняется при `qty_requested > available`; система обязана создать/обновить `ShortageSignal` + предложить/создать `ExternalHire` (сигнал «арендовать снаружи»);
- серийный контур не требуется для проведения заказа на MVP.

## 6. Roadmap фаз

### Фаза 0 — сейчас

- Research, архитектурный план, решения MVP
- **Нет** auth, БД, UI продукта в коде

### Фаза 1 — MVP (склад + заказы проката)

- Greenfield: справочник SKU, локации, остатки **qty**
- Движения склада (ручные; outbox на будущее)
- Заказы проката с датами и строками qty
- Soft-резервы + warning при overbook
- Нехватка → alert + поток **ExternalHire** («арендовать снаружи»)
- Абстракция Scan Events + заготовка webhook (без вендор-адаптера рамки)
- Роли склад + менеджер
- PWA на Next.js/TS

### Фаза 2 — сканирование и уведомления

- Подключение конкретной рамки/гейта через **generic adapter** (нормализация в ScanEvent)
- Web Push / notification bus для shortage и external_hire
- Календарь занятости парка по SKU, отчёты дефицита

### Фаза 3 — серийники, mapper, логистика

- Опциональный `track_mode: serialized` для выбранных SKU (панели и т.п.)
- Mapper sync
- Trips + hours
- Усиление offline; при необходимости Capacitor

### Фаза 4 — зрелость

- MDM/киоск, печать этикеток
- Расширенный RBAC и аудит
- Native-клиент склада только по метрикам боли PWA

## 7. Риски и митигация

| Риск | Митигация |
|------|-----------|
| Рамка AliExpress с «кривым» API | ранний контракт ScanEvent + тонкий адаптер; не тащить вендора в ядро |
| Soft overbook → хаос обязательств | явный статус ExternalHire и дашборд открытых нехваток; нельзя «тихо» игнорировать warning |
| Qty без серийников для дорогих панелей | заложить `track_mode` заранее; серийники включить точечно в фазе 3 |
| iOS Web Push слабее Android | склад на Android; критичные алерты дублировать в UI |
| Офлайн-конфликты qty | версия баланса + серверная валидация; conflict queue в UI |
| Дубли scan-событий | идемпотентный `event_id` |

## 8. Закрытые развилки и что ещё уточнить позже

**Закрыто** — см. [Решения MVP](#решения-mvp).

Некритично / можно уточнить ближе к реализации:

- формат поставщика внешней аренды (свободная заметка vs справочник контрагентов);
- пороги auto-создания ExternalHire vs только ручное подтверждение менеджером;
- конкретная модель рамки — когда появится, пишется адаптер, ядро не меняется;
- выбор облака и IdP.
